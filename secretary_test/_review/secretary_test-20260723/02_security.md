# 보안 감사 리포트

대상: `C:\Users\user\secretary_test`
날짜: 2026-07-23
감사 기준: OWASP Top 10, Supabase(Postgres+Auth+RLS) / Deno Edge Functions 보안
범위: 2026-07-01 종합 리뷰 이후 신규 추가된 3개 기능 — (1) 회사/부서 프로젝트 통합 화면, (2) 회원가입 회사관리자/직원 선택, (3) 일정/프로젝트 알림 메일 파이프라인. 기존 항목 재점검은 부록 참고.

## 요약

신규 기능 3종을 감사한 결과, **CRITICAL 1건 · HIGH 2건 · MEDIUM 3건 · LOW 2건**을 발견했다.

가장 심각한 문제는 알림 메일 파이프라인(schedule/project INSERT·UPDATE 트리거 → Edge Function)이 `client_ids` 배열의 소유권을 전혀 검증하지 않는다는 점이다. `schedules`/`projects` 테이블의 RLS는 행 자체(user_id)만 검증할 뿐 그 안에 담긴 `client_ids` 원소가 실제로 호출자 소유의 거래처인지는 검사하지 않으며, Edge Function은 Service Role 키로 이 배열을 그대로 조회해 이메일을 발송한다. 결과적으로 인증된 사용자라면 누구나 **다른 사용자의 거래처 ID를 자신의 일정/프로젝트에 끼워 넣는 것만으로 그 거래처의 이메일 주소를 알아내고, 임의의 제목·메모 내용으로 그 주소에 메일을 발송**시킬 수 있다. 이는 이 프로젝트가 핵심 설계 원칙으로 내세우는 "RLS 기반 계정 간 데이터 격리"를 정면으로 우회하는 경로다.

또한 회원가입 회사관리자 플로우는 `companies.name`에 유일성 제약이 없어, 누구나 실제 회사와 동일한 이름의 "가짜 회사"를 만들고 그 관리자가 될 수 있다. 신규 직원이 회사 목록 칩에서 이름만 보고 잘못된(가짜) 회사를 선택하면, 공격자는 `projects_select/update/delete_company_admin` RLS 정책을 통해 그 직원의 프로젝트를 정상적으로 열람·수정·삭제할 수 있게 된다 — 기술적 인가 우회가 아니라 **이름 충돌을 이용한 사회공학적 권한 탈취**이지만, 실행 난이도가 매우 낮고 피해가 크다.

반면 감사 대상으로 지정된 두 핵심 우려 사항 — ① `app.bypass_privilege_trigger` 세션 플래그를 클라이언트가 직접 켤 수 있는지, ② `signup_create_company_as_admin`으로 기존 회사를 탈취할 수 있는지 — 는 코드 검토 결과 **실제로는 안전**하다고 확인했다(검증된 안전 항목 참고).

## 검증된 안전 항목

이번 감사에서 사용자가 특히 우려한 두 지점을 집중 검증했고, 아래는 **문제없음으로 확인**된 항목이다.

1. **`app.bypass_privilege_trigger` 세션 플래그를 클라이언트가 직접 켤 수 있는가?** → **불가능함을 확인**. 이 플래그는 `perform set_config('app.bypass_privilege_trigger', 'true', true)`로 각 RPC 함수 내부에서만 설정되며, `is_local = true`(세 번째 인자)이므로 해당 트랜잭션 범위를 벗어나면 자동 소멸한다. Supabase JS SDK는 `supabase.rpc()`로 화이트리스트된 함수만 호출할 수 있고 임의 SQL 실행이나 `set_config` 직접 호출을 지원하지 않는다. `supabase/` 전체를 검색한 결과 `execute format`류의 동적 SQL 실행 RPC나 일반 SQL 실행을 허용하는 함수는 존재하지 않았다. `prevent_privileged_profile_self_update()` 트리거가 이 플래그를 검사하는 유일한 두 지점(`signup_create_company_as_admin`, `signup_join_company_as_employee`)은 각각 관리자/직원 값 고정 로직이 하드코딩되어 있어(아래 2, 3번), 이 예외 경로를 통한 셀프 승격은 불가능하다.
2. **`signup_create_company_as_admin`으로 기존 회사를 탈취할 수 있는가?** → **불가능함을 확인**. 이 함수는 항상 `insert into companies (name) values (...) returning id`로 새 `companies` 행을 만들고 그 `id`만 자신의 `company_id`로 설정한다. 기존 회사의 `id`를 지정하거나 검색해서 재사용하는 경로가 코드상 존재하지 않는다(단, 회사명이 겹칠 수 있다는 점은 발견 2번 참고 — "탈취"는 불가능하지만 "동명 회사 생성을 통한 사칭"은 가능).
3. **`signup_join_company_as_employee`에서 `is_company_admin`이 항상 false로 고정되는가?** → **확인됨**. `update profiles set ..., is_company_admin = false where id = auth.uid()`로 하드코딩되어 있어 이 경로로는 관리자 권한을 얻을 수 없다.
4. **`getCompanyProjects()`/`updateProjectAsCompanyAdmin()`/`deleteProjectAsCompanyAdmin()`이 `.eq('user_id', ...)` 없이 RLS에만 의존하는 구조가 실제로 견고한가?** → RLS 정책(`projects_select/update/delete_company_admin`)이 `my_is_company_admin()`(SECURITY DEFINER, `auth.uid()` 기준으로만 조회)과 `exists(select 1 from profiles p where p.id = projects.user_id and p.company_id = my_company_id())`를 함께 강제하므로, 일반 사용자(비관리자)가 이 함수들을 직접 호출해도 RLS가 0건으로 걸러낸다. `updateProjectAsCompanyAdmin`의 `changes` 인자는 `PROJECT_KEYMAP`을 통해서만 컬럼에 매핑되며 `user_id`는 이 맵에 없어 프로젝트 소유권 자체를 다른 회사로 이전하는 것도 불가능하다. **다만** 이 검증은 `my_company_id()`/`my_is_company_admin()` 헬퍼가 항상 최신 `profiles` 값을 반영한다는 전제이며, 발견 2번(동명 회사 사칭)이 성립하면 이 RLS 자체는 "설계대로" 작동하되 피해자가 잘못된 회사에 가입되어 있다는 문제로 우회된다.
5. **`companies_select_public`(전체 공개)이 민감정보를 노출하는가?** → `companies` 테이블에는 `id`(uuid), `name`, `created_at`만 존재하며 사용자가 우려한 대로 그 외 민감 컬럼이 없음을 스키마에서 확인. 미로그인 상태에서 회사 목록이 노출되는 것은 회원가입 UX상 의도된 동작이다.
6. **Pyannote 서버 URL의 `http://` 허용** (`src/services/groqStt.js:116,154`, `SettingsScreen.js:121` TODO 주석) — **기지(旣知) 항목, 의도적 보류**. `src/services/storage.js`의 `setPyannoteUrl()`은 이미 `isPrivateOrLocalHost()`로 사설 IP 대역(10.x/172.16-31.x/192.168.x/localhost)에 한해서만 HTTP를 허용하고 그 외에는 HTTPS를 강제하는 부분적 방어가 적용되어 있음을 확인했다. 다만 실제 전송 지점(`groqStt.js:116,154`)의 TODO 주석대로 이 검증이 저장 시점(`setPyannoteUrl`)에만 있고 전송 시점에는 재검증되지 않는 점은 그대로 남아 있다. 사용자가 로컬 네트워크 테스트 워크플로우를 위해 의도적으로 보류 중인 것으로 확인되어 이번 리포트에서는 **LOW로 하향**하고 신규 발견으로 집계하지 않는다.
7. **`.env`/`.env.local` 시크릿 커밋 여부** — `git ls-files`로 확인한 결과 두 파일 모두 git에 추적되지 않으며(`.env.example`만 추적됨), 히스토리에도 커밋 이력이 없다. `EXPO_PUBLIC_SUPABASE_ANON_KEY`는 RLS로 보호되는 공개 키라 노출되어도 무방하고, `EXPO_PUBLIC_PYANNOTE_API_KEY`는 앱 번들에 포함되는 구조적 한계(EXPO_PUBLIC_ 접두사)가 있으나 이는 2026-07-01 리뷰에서 이미 다뤄진 기존 항목이라 재집계하지 않는다.
